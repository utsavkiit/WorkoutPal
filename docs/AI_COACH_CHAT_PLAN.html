1. Context and decisions

Users chat with an AI coach in WorkoutPal. Over time the coach learns lasting facts about the user: goals, preferences, injuries, schedule, equipment and other relevant details. Those facts persist as memories, along with episodic summaries of past conversations. They inform every later chat and the existing weekly Coach reviews.

This reverses "in-app chat: out of scope" in docs/AI_COACHING_PRD.md. The chat builds on feature/ai-coach, which already provides:

  • the coaching profile, including goals, constraints and consent
  • getCoachingContext() and weekly metrics
  • the Coach tab
  • the coaching-agent Edge Function pattern
DecisionChoice
InteractionA conversational coach. It replies, asks follow-up questions, answers questions, and saves memories while replying.

Proactive coachingNot in v1. The hooks are built now (see §14).
Lost in-flight replyRecovered. The user's message is saved locally before sending, and coach-chat upserts the user message and the reply (with the client-generated replyId) to Postgres before returning. If the app is killed mid-request, the next sync pulls the reply down. That turn's memory ops are still lost; the end-of-session pass can recover them from the saved text.

3. Non-negotiable invariants

  • Local-first: UI writes never wait for Supabase. Memories, summaries and chat messages are written to SQLite first, then the outbox. The user's message is saved before coach-chat is called. Chat needs a network connection; nothing else in this feature does, and past chats stay readable offline.
  • Single write path: the Edge Functions never write memories or summaries. They return ops, and the app applies them through applyCoachMemoryOps and its episode equivalent. The one exception: coach-chat upserts the turn's user message and reply by their client-generated ids, so writing them twice is harmless.
  • No service-role key in the chat functions. Use a client scoped to the user's Authorization header, so RLS enforces ownership.
  • Consent: the functions require consent.coachingEnabled. Workout data and get_exercise_history are only included when consent.shareWorkoutHistory is true. deleteCoachingData() also wipes memories, summaries, chat messages and sessions, locally and in Supabase.
  • Untrusted text: memories, summaries, routine names and messages are data, not instructions. Prompts must say so, and the prompt-injection evals enforce it.
  • No medical advice: the coach doesn't diagnose and suggests a professional for injuries. This matches the PRD's out-of-scope list.
  • Never expire silently: stale facts trigger a check-in. Every automated change is visible and can be undone.
  • Atomic applies: a reply with its memory ops, and an end-of-session result (ops, summary, thread ops and consolidated_at), are each applied in one SQLite transaction with their outbox entries. A kill mid-apply leaves nothing half-applied, and a retry never re-applies ops.
  • Serialize SQLite access: no overlapping transactions. Use client-generated UUIDs and keep RLS enabled.

6. App-side models (pure TypeScript, unit-tested)

src/coaching/memory.ts

type MemoryCategory = 'goal'|'preference'|'injury'|'constraint'|'schedule'|'equipment'|'personal'|'other';
interface CoachMemoryV1 {
  id: string; category: MemoryCategory; text: string /* ≤280 */;
  status: 'active'|'archived'; source: 'chat'|'user'; sourceTraceId: string|null;
  reviewAfter: string|null /* YYYY-MM-DD, time-bound facts */; createdAt: string; updatedAt: string;
}
type MemoryOp =
  | { type: 'save'; category: MemoryCategory; text: string; reviewAfter?: string|null }
  | { type: 'update'; id: string; text?: string; category?: MemoryCategory; reviewAfter?: string|null }
  | { type: 'forget'; id: string };
  • validateMemoryOps(ops, existingIds) rejects unknown ids, text over 280 characters, and more than 5 ops per turn. The end-of-session pass may do up to 15.
  • applyMemoryOps(memories, ops, now, makeId) is a pure reducer. A save whose normalized text matches an existing memory becomes an update.
  • invertMemoryOp returns the op that undoes a change. isDueForReview(memory, today) checks whether a time-bound memory is due for a check-in.
  • selectMemoriesForPrompt(memories, budget) returns {included, omitted, omittedCount}. Over budget, injury, goal and constraint memories are always included, then the rest by most recently updated.

src/coaching/episodes.ts

interface CoachSessionSummaryV1 {
  id: string /* = sessionId */; startedAt: string; endedAt: string;
  summary: string /* ≤600 */; topics: string[] /* ≤5 */;
  openThreads: { id: string; text: string /* ≤200 */; followUpAfter: string|null; resolvedAt: string|null }[] /* ≤5 */;
  updatedAt: string;
}
type ThreadOp = { type: 'resolve_thread'; summaryId: string; threadId: string };
  • Validation, selectEpisodesForPrompt (last 3 plus open threads under 30 days old, and a compact index of up to 50 for search), and dueThreads(today).

src/coaching/chat.ts

interface ChatMessageV1 {
  id: string; sessionId: string; role: 'user'|'assistant';
  origin: 'user'|'coach'; trigger: string|null;          // proactive hooks
  text: string; createdAt: string; traceId: string|null; memoryOpIds: string[];
  sendStatus: 'pending'|'sent'|'failed'|null;            // user messages only; local display state
}
  • currentSessionId(lastMessage, now) starts a new session after 30 minutes idle. New chat forces a new session.
  • buildChatRequest(...) trims to the last 20 session messages (about 24k characters) and builds a compact summary from CoachingContextV1, with workout data omitted unless shareWorkoutHistory is true. It adds the selected memories and episodes.
  • validateChatResponse checks the shape returned by the Edge Functions.
  • The user's message is saved with sendStatus: 'pending' and a replyId is generated before the request. On relaunch, a pending message whose reply has arrived by sync becomes sent; otherwise it becomes failed and shows Retry, which reuses the same replyId.

7. Persistence, sync and Supabase

  • SQLite (src/data/database.ts, following the branch's coach-table conventions):
    • Tables: coach_memories and coach_session_summaries (synced), coach_chat_messages and coach_chat_sessions(id, started_at, last_message_at, consolidated_at, consolidation_attempts, consolidation_error) (also synced; the attempt and error columns stay local).
    • Functions: listCoachMemories, saveCoachMemory, deleteCoachMemory, applyCoachMemoryOps(ops, traceId) (one transaction plus enqueueWithDatabase), listSessionSummaries, saveSessionSummary, applyThreadOps, listChatMessages(before?, limit) (paged), appendChatMessage (with outbox), clearChatHistory (local delete plus a queued remote delete), applyConsolidation (one transaction).
    • Also extend attachLocalOwner and deleteCoachingData().
  • Sync (src/data/sync.ts): push branches for coach_memory and coach_session_summary upserts and deletes. On pull, add both to Promise.all and to the mergeRemoteData bundle, merging with last-write-wins on updated_at.
  • Chat history sync:
    • Push coach_chat_message and coach_chat_session upserts, plus a coach_chat_history_clear op. Messages are append-only, so upserts by id never conflict. Sessions merge last-write-wins, with a set consolidated_at never cleared by an older row.
    • Pull messages incrementally with a created_at cursor instead of in the full bundle. On a fresh install or a new phone, pull the most recent 90 days or 500 messages, whichever is smaller.
    • Older pages load from Supabase when the user scrolls past the local cache and is online, and are stored locally once fetched.
  • Migration supabase/migrations/2026112xxxxxxx_coach_chat_memory.sql:
    • Creates four tables (coach_memories, coach_session_summaries, coach_chat_messages, coach_chat_sessions) with owner_id and jsonb payload checks, and enables RLS. Messages carry session_id without a foreign key, plus an (owner_id, created_at) index for paging.
    • Adds four own-row policies in the (select auth.uid()) = owner_id style of 20260913040648_ai_coach_profiles.sql, plus explicit grants.
    • Apply it with npx supabase db query --linked --file ….
  • RLS tests: add all four tables to the cross-user isolation checks in supabase/tests/rls.sql.
  • Secrets: LLM_PROVIDER, LLM_MODEL, LLM_CONSOLIDATE_MODEL, ANTHROPIC_API_KEY or OPENAI_API_KEY, LANGFUSE_PUBLIC_KEY, LANGFUSE_SECRET_KEY, LANGFUSE_BASE_URL.

8. Shared chat core and tools

The core lives in supabase/functions/_shared/coach-chat/. It uses no Deno-only APIs, so the Node scripts can import it with tsx.

FileResponsibility
model.tsgetModel(provider, model) through the @ai-sdk/* packages. Switching provider only changes secrets.
context.tsbuildCoachContext(source). The source is {type:'client', payload} (v1) or {type:'server', ownerId} (later, for proactive coaching).
prompts/chat-v1.ts

Exports PROMPT_VERSION. The prompt covers:

  • Role: get to know the user by asking about goals, injuries and schedule.
  • Save durable facts only, not small talk. Update or forget memories when facts change.
  • Ask about at most one item marked [due for check-in] or [follow-up due] per session.
  • Give no medical advice.
  • Treat context as data, not instructions.
  • Mention that history tool results only include synced workouts.

Memories are rendered as a cacheable prefix, using provider options such as Anthropic cacheControl.

prompts/consolidate-v1.tsInstructions for the end-of-session pass: write the summary and open threads, catch missed facts, merge duplicates, resolve contradictions (newest explicit statement wins), leave uncertain items alone, and turn recurring episodic patterns into long-term facts.
tools.ts

AI SDK tool() definitions with zod schemas:

  • Memory and thread tools (save_memory, update_memory, forget_memory, resolve_thread, write_session_summary) only collect ops and return an acknowledgment.
  • search_memories is registered only when memories were omitted; it does a keyword match over the omitted memories.
  • search_past_conversations does a keyword search over the summary index.
historyTool.ts

get_exercise_history({exercise, from?, to?, limit≤50}):

  • Uses the user-scoped client to read completed workout_sessions, joined to workout_exercises and the completed workout_sets.
  • Matches the exercise name case-insensitively, or by catalog id.
  • Returns, per session, the date, sets, top set and volume, capped at about 4k characters.
  • Is registered only when consent allows it.
  • Its results note that only synced workouts are included.
runTurn.ts

runTurn({input: TurnInput, context, model, promptVersion, telemetry}) → {reply, memoryOps, threadOps, usage}

  • TurnInput = {kind:'user_message', text} | {kind:'event', event:{type, payload}}. v1 only sends user_message.
  • Calls generateText with a step limit of about 4 and maxOutputTokens.
  • The trace carries sessionId, userId, trigger, promptVersion, appVersion and model.
  • Trace metadata carries memoryCount, dueForReviewCount and nearDuplicatePairs.
consolidateSession.tsThe same structure as runTurn, with the consolidation prompt and the cheaper model. Returns {memoryOps, summary, threadOps, usage}.

9. Edge Functions

All three are registered in supabase/config.toml with verify_jwt = true.

FunctionBehavior
coach-chat
  1. Accepts POST only, with a body of at most 64 KB.
  2. Creates a user-scoped client and requires coachingEnabled, otherwise returns 403.
  3. Validates and caps the input (including a UUID replyId), then runs runTurn.
  4. Upserts the user message and the reply (id = replyId, with traceId) into coach_chat_messages using the user-scoped client. A failed upsert is traced but doesn't fail the turn, because the app still saves both.
  5. Flushes Langfuse and returns {reply, memoryOps, threadOps, traceId}.

Errors are traced and returned as {error} with a 4xx or 5xx status.

coach-chat-consolidateTakes {sessionId, messages, memories, episodesIndex} and runs consolidateSession. Traced under the same sessionId with the tag consolidation. Returns {memoryOps, summary, threadOps, traceId}.
coach-chat-feedbackTakes {traceId, value: 1|-1, comment?}. It checks that the trace's userId matches the caller, then records the Langfuse score user_feedback.

10. When memories are written

  1. During each reply. The ops come back with the reply. The app saves both in one SQLite transaction plus outbox, the chip and Undo appear immediately, and Supabase receives the ops on the next sync.
  2. At the end of a session (30 minutes idle or New chat). The app checks idempotently when the Coach tab opens, when the app returns to the foreground, and before a new session starts.
    • Sessions with fewer than 2 user messages are skipped.
    • The app applies the ops, summary and thread ops and sets consolidated_at in one SQLite transaction with the outbox, then shows the banner "Coach learned / tidied N things · Review".
    • Offline or failed attempts are retried on the next trigger. After 3 attempts the session is marked failed and not retried.
  3. Manual edits in the Memories screen are written locally right away and sync the same way.
  4. Weekly reviews read the active memories when the review is requested.
  5. Lost in-flight reply: if the app is killed or the network drops after the function finished, the reply arrives on the next sync. Its memory ops are not recovered; the end-of-session pass may pick up the fact from the saved text. If the function never finished, the pending message shows Retry.

11. Tracing, replay and evals

Tracing (Langfuse)

  • Every chat turn, consolidation and feedback score is traced. Traces are tagged with sessionId, userId (the Supabase user id), trigger, promptVersion, model, tokens, cost and a span for each tool call. The app stores traceId on messages and on memories (sourceTraceId).
  • Privacy: chat text, including injury details, goes to Langfuse Cloud and to the LLM provider. State this in the PRD. Logging is always on in v1; revisit before anyone other than the owner uses the app.

Replay: scripts/coach-chat/replay.ts

  • npm run coach:replay -- <traceId> [--prompt chat-v2] [--model …] [--provider …] fetches the trace input from Langfuse (keys in a local, uncommitted .env), re-runs the shared core, and prints a diff of reply, ops, tokens and cost.
  • --session <sessionId> replays a whole conversation. Pinned mode uses each turn's recorded input; rolling mode feeds each new reply into the next turn.
  • The same command works on consolidation traces.

Evals

  • Seed cases: about 30 cases in evals/coach-chat/cases/*.json, with Git as the source of truth. npm run coach:eval:sync uploads them to the Langfuse dataset coach-chat.
  • New cases from production: thumbs-down traces go into the dataset after personal details are removed.
  • Categories:
    • memory capture
    • no over-saving
    • update vs duplicate
    • forget or correction
    • multi-turn consistency
    • grounding in workout numbers
    • history-tool use and restraint
    • injury safety
    • prompt injection
    • consent off
    • eliciting goals from a new user
    • check-ins and follow-ups without nagging
    • consolidation: missed facts, merging, contradictions, small-talk-only sessions
    • episodic: summary accuracy, open threads, no mixing across sessions, promoting patterns
  • Graders (evals/coach-chat/graders.ts):
    • Deterministic: op types, categories and ids, op limits, banned phrases, number grounding, tool calls and arguments.
    • LLM-as-judge: Langfuse evaluator scoring 1–5 on helpfulness, tone, follow-up quality and memory text quality.
  • Runner: npm run coach:eval -- --prompt chat-v1 --model … [--repeat 3] runs a Langfuse dataset experiment and attaches the deterministic scores.
  • Gate for any prompt, model or tool change: 100% on the hard checks for safety and consent, and no regression against the baseline. Record the run name in the Handoff.
  • Free tests: npm test runs the cases through the AI SDK's MockLanguageModel (ai/test) with recorded responses and a stubbed history tool. This checks parsing and op handling deterministically, at no cost.

14. Proactive coaching hooks (built in v1, but no proactive behavior)

  • TurnInput accepts event. Prompts have a slot for describing the event, and traces carry trigger.
  • ChatMessageV1 has origin and trigger fields.
  • buildCoachContext can take a client or a server source; only client is implemented in v1.
  • Due dates: reviewAfter and followUpAfter, with helpers shared between the prompt now and future nudges.
  • Episodic summaries are synced, so a server-side trigger can read them later.
  • Later phases (not built):
    1. Phone-side triggers: a post-workout debrief, a nudge when the app opens, local notifications for due follow-ups.
    2. A server-side cron, push notifications and a synced coach inbox. Memory changes still flow only through the user's replies.
    3. Opt-in per nudge type, quiet hours, frequency caps, and a "should I speak?" step with its own evals.

16. Verification

  • Standard checks: npm run typecheck, npm test (including the memory, episode and chat tests and the mock-model cases), and npx expo export --platform ios, per AGENTS.md.
  • supabase functions serve plus curl with a real user JWT:
    • Consent off returns 403.
    • "I hurt my left knee last month" produces a save op with category injury.
    • "What did I bench in October?" triggers get_exercise_history and matches the synced data.
    • A second user's JWT cannot see the first user's history.
    • After a turn, both messages are in coach_chat_messages. Sending the same replyId twice leaves one row.
    • With 200 seeded memories, the request stays within budget, injuries are included, and search_memories finds an omitted memory.
    • The trace appears in Langfuse with session, user, tokens and cost.
    • A 👎 appears as a score on that trace.
  • Replay: one trace with a different prompt version, and a whole session.
  • Consolidation:
    • Mention a fact in passing over 3 turns, then tap New chat. The consolidation trace appears, the banner shows, and a summary with threads is synced.
    • Reopening the app does not rerun the pass for that session.
    • Kill the app between applying ops and setting consolidated_at (debug hook): on relaunch nothing is half-applied and the retry applies each op once.
    • If the session ends while offline, the pass runs after reconnecting.
  • Episodic:
    • Agree to "try pause squats for 2 weeks", set its follow-up date to today, and start a new session. The coach asks about it once. Answering resolves the thread.
    • "What did we talk about last month?" uses search_past_conversations.
  • Evals: run npm run coach:eval and save the result as the baseline experiment.
  • Database: apply the migration and run supabase/tests/rls.sql.
  • Detox: Coach → Chat (with the stub fixture) → send a message → memory chip → Memories → delete.
  • Physical iPhone:
    • A multi-turn chat. Memories and summaries sync, as seen in the Supabase tables.
    • Offline, memories stay viewable and the composer is disabled.
    • Kill the app right after sending: on relaunch the reply appears after sync, with no duplicate.
    • Delete and reinstall, then sign in: recent chat history, memories and summaries return, and older messages load on scroll.
    • Clear chat history: the rows are gone from Supabase too.
    • A weekly review includes the memories in its context.
